## Conceitos Básicos

### O que é Teste?

Existem várias definições comuns para teste de software, mas nenhuma captura completamente a essência:

1. **Testar é demonstrar ausência de erros** — Definição limitada que foca apenas na execução.
2. **Testar é mostrar execução correta** — Foca na conformidade com especificações.
3. **Testar é estabelecer confiança** — Abordagem mais holística, mas vaga.

**Definição de Glenford Myers (1979):**

> Testar é o processo de executar um programa de software com a intenção de encontrar erros.

Esta é a definição mais usada na indústria porque estabelece claramente o **objetivo central**: encontrar defeitos, não provar que o software está correto.

### Teste é Mais que Execução

Um erro comum é pensar que teste = executar casos de teste. Na verdade, **teste de software é um processo holístico** que inclui:

- **Planejamento de teste**: definir escopo, objetivos, recursos e cronograma
- **Análise**: entender requisitos, identificar riscos e prioridades
- **Modelagem**: desenhar estratégias, casos de teste e dados
- **Implementação**: codificar testes automatizados ou preparar roteiros manuais
- **Execução**: rodar os testes e coletar dados
- **Avaliação**: verificar resultados contra o esperado
- **Relatórios**: comunicar achados e métricas
- **Melhoria contínua**: otimizar o processo de teste

A execução é apenas uma parte deste ciclo.

## Terminologia Fundamental

### Testes Estáticos vs. Dinâmicos

#### **Teste Estático**

Atividade que contempla **apenas revisão** de artefatos, **sem executar o software**.

**Tipos:**

- **Revisão**: leitura crítica de documentos/código por um desenvolvedor
- **Walkthrough**: apresentação do código por seu autor a colegas
- **Inspeção**: revisão formal com checklist definido (mais rigorosa)

**Exemplos de produtos testados estaticamente:**

- Requisitos e casos de uso
- Arquitetura e design
- Código fonte
- Manual do usuário
- Documentação técnica

**Vantagens:**

- Detecta defeitos cedo, antes da compilação
- Identifica problemas de design e requisitos
- Custa menos do que corrigir em fases posteriores

#### **Teste Dinâmico**

Atividade que envolve **execução do software**, fornecendo entradas e avaliando saídas.

**Tipos:**

- **Funcionais**: verifica se o software faz o que deve fazer
- **Não-funcionais**: verifica performance, segurança, usabilidade, etc.

**Vantagens:**

- Detecta falhas reais em tempo de execução
- Valida comportamento em ambiente real
- Identifica problemas de interação complexa

---

### A Tríade: Erro → Defeito → Falha

Esta é uma distinção **crítica** para entender testes:

```
DESENVOLVEDOR    CÓDIGO      SISTEMA      USUÁRIO
    ↓             ↓          ↓            ↓
   ERRO       →  DEFEITO  →  FALHA   →  IMPACTO
```

#### **Erro (Mistake)**

Uma **ação humana incorreta** que produz um resultado indesejado.

**Exemplos:**

- Desenvolvedor escreve `if (x = 5)` em vez de `if (x == 5)` por falta de atenção
- Testador interpreta requisito ambíguo de forma errada
- Arquiteto escolhe padrão inadequado para o contexto

**Causas comuns de erros:**

- **Ignorância/Falta de conhecimento**: não saber a linguagem ou ferramenta
- **Pressão de tempo**: deadlines apertados que induzem pressa
- **Negligência**: falta de cuidado ou atenção
- **Inexperiência**: pouco tempo no projeto ou na área
- **Complexidade**: problema é tão complexo que confunde
- **Mal-entendido**: interpretação equivocada de requisitos
- **Falha de comunicação**: informação perdida ou distorcida

#### **Defeito (Bug/Fault)**

Uma **imperfeição ou deficiência** em um produto de trabalho (código, design, documento) **causada por um erro**.

**Exemplos:**

- Código contém a instrução `if (x = 5)` (defeito do código)
- Documento de requisitos é ambíguo (defeito do artefato)
- Design não contempla caso de uso específico (defeito de design)

**Características:**

- Pode existir no código sem ser ativado (defeito latente)
- Pode ser documentado e rastreado
- Pode ser removido através de correção

#### **Falha (Failure)**

Um **evento observável** onde o sistema não executa uma função conforme os requisitos estabelecidos.

**Exemplos:**

- Usuário clica em botão e a função não funciona
- Sistema retorna resultado incorreto
- Aplicação congelou ou crasheou
- Performance está inaceitável

**Características:**

- É observável pelo usuário ou tester
- Indica que pelo menos um defeito foi ativado
- Causa impacto direto na experiência

---

### Análise de Causa-Raiz (RCA)

**Root-Cause Analysis** é a prática de investigar profundamente um defeito para identificar suas **causas-raízes** — as condições primeiras que o originaram.

**Processo típico de RCA:**

1. Ocorre uma falha (observação do problema)
2. Identifica-se o defeito (raiz técnica)
3. Investiga-se por quê o defeito existe (processo, conhecimento, comunicação)
4. Implementam-se ações de melhoria
5. Implementam-se controles para evitar repetição

**Exemplo prático:**

- Falha: Sistema não processa pagamento
- Defeito: Função de validação de cartão retorna exceção não tratada
- Causa-raiz: Desenvolvedor não conhecia biblioteca de validação
- Ação: Treinamento + revisão de código + documentação

**Efeitos da falha** (impactos de negócio):

- Reclamações de clientes
- Perda de receita
- Danos à reputação
- Custos de suporte e correção

### Artefatos de Teste

#### **Caso de Teste**

Um **conjunto completo** que define como testar um requisito específico.

**Componentes:**

- **Pré-condições**: estado necessário antes de iniciar (dados, ambiente)
- **Procedimentos**: passos exatos a executar (entradas)
- **Resultado esperado**: qual deve ser a saída/comportamento correto

**Exemplo:**

```
Caso: Validação de Login
Pré-condições: Usuário não autenticado; usuário "jose@email.com" existe
Procedimento:
  1. Acessar tela de login
  2. Digitar email: "jose@email.com"
  3. Digitar senha: "123456"
  4. Clicar botão "Entrar"
Resultado esperado: Sistema autentica, redireciona para dashboard
```

#### **Suíte de Teste**

Um **conjunto lógico** de casos de teste que devem ser executados em ordem.

**Exemplo:**

```
Suíte: Autenticação
  ├─ Caso: Login com credenciais válidas
  ├─ Caso: Login com email inválido
  ├─ Caso: Login com senha incorreta
  ├─ Caso: Logout
  └─ Caso: Sessão expira após timeout
```

**Benefícios:**

- Organização clara
- Rastreabilidade
- Reutilização
- Priorização

#### **Plano de Teste**

Um **documento de planejamento** que define como testes serão executados.

**Conteúdo típico:**

- **Escopo**: o que será testado, limites
- **Abordagem**: estratégia de teste (manual vs. automatizado, etc.)
- **Recursos**: pessoal, ferramentas, ambientes
- **Cronograma**: timeline e marcos
- **Funções**: quem faz o quê
- **Ambiente**: tecnologias, configurações
- **Motivação de escolhas**: por que essa estratégia
- **Riscos**: o que pode dar errado
- **Plano de contingência**: como reagir a riscos

---

### Verificação vs. Validação

Conceitos frequentemente confundidos, mas **fundamentalmente diferentes**:

#### **Verificação**

> "Estamos construindo o produto **da maneira certa?**"

**O que é:** Processo de avaliar se documentos, artefatos e software **atendem aos requisitos especificados**.

**Foco:**

- Verificar conformidade com especificações
- Garantir que o design é correto
- Validar que o código implementa o design
- Atividade interna

**Exemplo:**

- Revisar se o código implementa exatamente o design especificado
- Verificar se o design cobre todos os requisitos

#### **Validação**

> "Estamos construindo o **produto certo?**"

**O que é:** Processo de avaliar se o software **satisfaz as necessidades reais do usuário** em seu ambiente de uso.

**Foco:**

- Testar se o software faz o que o usuário precisa
- Garantir usabilidade e satisfação
- Validar em ambiente real ou similar
- Atividade externa (envolvendo stakeholders)

**Exemplo:**

- Testar com usuários reais se o sistema é fácil de usar
- Validar se o software resolve o problema de negócio

**Diferença crucial:** Um software pode estar **verificado** (segue todas as especificações) mas não **validado** (não resolve o problema real do usuário). E vice-versa, um software pode ser validado (útil) mas não verificado (não segue padrões).

## Psicologia do Teste

### Teste como Processo Destrutivo

O teste busca **encontrar o que não funciona**, o que é fundamentalmente diferente da mentalidade de construção.

**Dinâmica psicológica:**

- Testador: porta más notícias (teste falhou)
- Desenvolvedor: percebe como crítica pessoal
- Resultado: tensão entre times

**Perigos:**

- Desenvolvedor se defende em vez de corrigir
- Qualidade é vista como inimiga do desenvolvimento
- Correções apressadas levam a mais defeitos

---

### Mudança de Mentalidade: Dev vs. QA

#### **Mentalidade de Desenvolvedor**

- Objetivo: construir algo que funcione
- Bias: "Este código está bom"
- Foco: fazer funcionar
- Teste: verificar happy path

#### **Mentalidade de Testador**

- Objetivo: encontrar o que não funciona
- Bias: "Como quebrar isso?"
- Foco: casos extremos e edge cases
- Teste: explorar todos os caminhos

**Por que importa:** Quando o próprio desenvolvedor faz testes unitários (shift-left), ele precisa **conscientemente mudar de mentalidade**. Testes escritos por devs com mentalidade construtiva são frágeis e não encontram defeitos.

---

### Comunicação Construtiva

A solução para reduzir tensão é **comunicação colaborativa**:

**Princípios:**

1. **Atividade Colaborativa**
    
    - Objetivo comum: construir sistemas de qualidade
    - Teste é parceria, não competição
    - "Nós" contra o problema, não "Eu" contra "Você"
2. **Enfatizar Benefícios**
    
    - Para o desenvolvedor: informação sobre defeitos melhora suas habilidades
    - Feedback = oportunidade de aprender
    - Defeito encontrado agora = cliente satisfeito depois
3. **Relatórios Neutros**
    
    - Focar em fatos: "Quando X ocorre, Y acontece"
    - Evitar julgamentos: "código ruim", "desenvolvedor incompetente"
    - Descrever o problema, não a pessoa
    - Exemplo: ❌ "Você implementou errado" vs. ✅ "Quando entrada é vazia, a função retorna exceção em vez de mensagem de erro"
4. **Confirmar Entendimento**
    
    - Verificar se desenvolvedor compreendeu o defeito
    - Discutir solução juntos
    - Acordar critérios de aceitação da correção

## Os 7 Princípios do Teste de Software

Estes princípios formam a **base teórica moderna** de teste de software (ISTQB):

### Princípio 1: Teste Mostra Presença de Defeitos, Não Ausência

> Teste reduz a probabilidade de defeitos não descobertos, mas **nunca prova que não há defeitos**.

**Implicação:**

- Um teste que passa = "nenhum defeito foi encontrado nesta condição"
- Não significa "nenhum defeito existe"
- Cobertura 100% de código ≠ software sem defeitos

**Por quê:**

- Impossível testar todas as combinações possíveis
- Defeitos podem estar em interações não testadas
- Requisitos podem estar incompletos ou errados

**Aplicação prática:**

- Mantenha humildade: teste faz seu melhor, mas não é garantia
- Invista em prevenção (design, code review, testes estáticos)
- Use múltiplas técnicas: unitário, integração, sistema, etc.

---

### Princípio 2: Testes Exaustivos São Impossíveis

> Não é viável testar **todas** as combinações de entrada e pré-condições.

**Exemplo matemático:** Uma função simples que recebe 3 parâmetros inteiros teria 2³² × 2³² × 2³² combinações possíveis. Testar uma por ms levaria séculos.

**Alternativa: Teste Inteligente**

Em vez de exaustivo, usa-se:

1. **Análise de Risco**
    
    - Identificar áreas de maior risco
    - Focar esforço lá
    - Aceitar risco calculado em áreas baixo-risco
2. **Técnicas de Teste**
    
    - Particionamento de equivalência
    - Análise de valores limite
    - Teste de caminhos críticos
    - etc.
3. **Priorização**
    
    - Funcionalidades críticas primeiro
    - Casos de uso comuns
    - Regiões de código complexo

**Aplicação prática:**

- Defina escopo realista de teste
- Use riscos para priorizar
- Documente o quê **não** será testado e por quê

---

### Princípio 3: Teste Inicial Economiza Tempo e Dinheiro

> Quanto **antes** encontrar defeitos no ciclo de vida, **menor** o custo de correção.

**Linha do tempo de custo:**

```
Fase            Custo de Correção
Requisitos      $100
Design          $1,000
Código          $10,000
Testes          $100,000
Produção        $1,000,000+
```

**Conceito de Shift-Left:** "Deslocar" testes para a **esquerda** no timeline (para fases iniciais).

**Estratégia:**

1. **Testes Estáticos Cedo**: revisar requisitos e design com QA
2. **Testes Unitários**: desenvolvedores testam enquanto codificam
3. **Integração Contínua**: rodar testes automatizados a cada commit
4. **Teste de Sistema**: quando integração está estável

**Exemplo de impacto:**

- Defeito de requisito encontrado no design: custa corrigir especificação
- Mesmo defeito encontrado em produção: custa refazer código, testes, deploy, suporte ao cliente

**Aplicação prática:**

- Inclua QA desde o planejamento, não no final
- Automatize testes de regressão
- Integrate testes no pipeline de CI/CD

---

### Princípio 4: Defeitos Se Agrupam

> Um **pequeno número de módulos** contém a maioria dos defeitos.

**Padrão observado (Lei de Pareto):**

- 80% dos defeitos estão em 20% do código
- Alguns módulos têm 10x mais defeitos que outros
- Padrão previsível: código legado, complexo, mal documentado

**Por quê:**

- Código complexo tem mais caminhos, maior chance de erro
- Código legado tem menos testes
- Pressão de tempo = refatoração de qualidade pior
- Falta de conhecimento = erros sistemáticos

**Aplicação prática:**

1. **Analyze** histórico de defeitos
2. **Identify** módulos problemáticos
3. **Focus** esforço de teste nesses módulos
4. **Refactor** ou reescrever módulos críticos

**Combinação com Princípio 2:** Não teste exaustivamente tudo, teste **exaustivamente os módulos de alto risco**.

---

### Princípio 5: Cuidado com o Paradoxo do Pesticida

> Se **mesmos testes** são repetidos, **novos defeitos não serão encontrados**.

**Analogia:**

- Pesticida mata insetos
- Insetos sobreviventes se reproduzem resistentes
- Pesticida não mata mais

**No contexto de teste:**

- Seu teste suite passa
- Você não muda os testes
- Próximo release: testes ainda passam, mas há novos defeitos
- Por quê? Os testes só cobrem os cenários anteriores

**Solução:**

1. **Evoluir testes**: atualizar casos quando código muda
2. **Adicionar novos testes**: explorar novo código
3. **Técnicas criativas**: pensar em novos casos de falha
4. **Code reviews**: discutir cenários antes de codificar

**Exceção benéfica: Testes de Regressão** Testes de regressão _são_ repetidos (propositalmente), e isso é bom porque:

- Garante que correção anterior não foi quebrada
- Número baixo de defeitos de regressão é desejado

**Aplicação prática:**

- Revise suite de testes regularmente
- Adicione testes para cada novo bug encontrado
- Discuta novos cenários em code review

---

### Princípio 6: O Teste Depende do Contexto

> Teste é **diferente** em diferentes situações.

**Exemplos de contextos diferentes:**

1. **Crítico vs. Não-Crítico**
    
    - Software de controle médico: testes rigorosos, documentação formal
    - App de jogo casual: testes ágeis, foco em user experience
    - Bancos: testes de segurança intensivos
    - E-commerce: testes de performance e concorrência
2. **Metodologia**
    
    - Ciclo sequencial (Waterfall): testes formais, documentação pesada
    - Ágil (Scrum): testes contínuos, feedback rápido
    - DevOps: automação, testes em produção, canary releases
3. **Tipo de Software**
    
    - Web: testes de browser, responsividade
    - Móvel: testes de bateria, conectividade
    - Embedded: testes de hardware, real-time
    - Dados: testes de integridade, performance
4. **Estágio do Projeto**
    
    - Protótipo: teste exploratório, rápido
    - Produção: teste exaustivo, documentado
    - Maintenance: teste de regressão, automação

**Implicação:**

- Não existe "one size fits all"
- Adapte estratégia ao contexto
- Comunique trade-offs (velocidade vs. qualidade)

---

### Princípio 7: Ausência de Erros É Uma Ilusão

> Encontrar e corrigir **todos** os defeitos **não garante** sucesso do sistema.

**Paradoxo:** Um software pode estar 100% correto em relação aos requisitos mas ainda falhar porque:

1. **Requisitos estão errados**
    
    - Clientes não conseguem articular necessidades reais
    - Requisitos mudam durante desenvolvimento
    - Requisitos conflitam com outros critérios
2. **Qualidade ≠ Funcionalidade**
    
    - Software "correto" mas impossível de usar
    - Performance inaceitável
    - Segurança negligente
    - Experiência de usuário ruim
3. **Competição**
    
    - Seu software é correto mas concorrente é melhor
    - Clientes mudam por falta de features, não por bugs

**Exemplo real:** Versão 1.0 de Windows Vista estava "tecnicamente correta" mas fracassou porque:

- Lento (performance)
- Difícil de instalar (usabilidade)
- Incompatível (ecosistema)

**Implicação:**

- Teste não é responsável por sucesso, mas é parte crítica
- Outros fatores: design, UX, marketing, suporte
- "Qualidade" é multidimensional

**Aplicação prática:**

- Não seja dogmático sobre testes
- Balanceie teste com outras atividades
- Meça sucesso além de "bugs encontrados"

## Regra 10 de Myers

**Glenford Myers, 1979**, propôs:

> É necessário **~10x mais esforço** para identificar, corrigir e verificar um defeito encontrado em teste do que **prevenir** esse defeito no início do desenvolvimento.

**Desdobramento:**

```
Fase           Esforço Necessário
Requisitos     1 unidade (prevenir)
Design         1 unidade (prevenir)
Código         1 unidade (prevenir)
Testes         10 unidades (encontrar + corrigir)
Produção       100+ unidades (encontrar + corrigir + impacto)
```

**Por quê multiplicar 10x:**

1. **Encontrar o defeito**: rodar testes, reproduzir, investigar
2. **Entender a causa**: debugar, entender interações
3. **Corrigir**: modificar código
4. **Verificar correção**: rodar testes afetados
5. **Regressão**: garantir que correção não quebrou algo
6. **Deploy**: reiniciar ambientes, comunicar mudanças
7. **Impacto**: possível perda de dados, indisponibilidade

**Justificativa para Shift-Left:**

Se custa 10x menos prevenir, então deve-se:

1. Investir em **design de qualidade**
2. Investir em **code review**
3. Investir em **testes estáticos** cedo
4. Investir em **testes unitários** durante código
5. Minimizar testes de sistema (encontram defeitos caros)

**Mensagem Central:**

> Foco de QA não é encontrar e corrigir defeitos, mas **preveni-los desde o início**.

## Modelo V

O **Modelo V** é uma representação visual de como testes se conectam com fases de desenvolvimento.

### Estrutura

```
DESENVOLVIMENTO (Esquerda)          TESTE (Direita)
        ↑                                  ↓
    Requisitos  ←→  Teste de Aceitação (UAT)
        ↑                                  ↓
    System Design  ←→  Teste de Sistema
        ↑                                  ↓
    Architecture  ←→  Teste de Integração
        ↑                                  ↓
    Module Design  ←→  Teste Unitário
        ↑                                  ↓
       Código ←→ Execução
```

### Lógica

Cada **nível de desenvolvimento** tem um **nível de teste correspondente**:

|Fase de Dev|Artefato|Teste Correspondente|Valida|
|---|---|---|---|
|Requisitos|Especificação|Teste de Aceitação|Se resolve o problema|
|Design de Sistema|Arquitetura|Teste de Sistema|Se funciona end-to-end|
|Design de Arquitetura|Componentes|Teste de Integração|Se componentes trabalham juntos|
|Design de Módulo|Funções|Teste Unitário|Se função funciona isolada|
|Código|Implementação|Execução|Se compila|

### Aplicação

1. **Planejamento paralelo**: enquanto design é feito, já defina testes
2. **Testes estáticos cedo**: revisar requisitos com QA antes de codificar
3. **Testes dinâmicos progressivos**: começar com unitários, crescer para sistema

## Níveis de Teste

Os **4 níveis clássicos** formam a pirâmide de testes e o Modelo V.

### 1. Teste Unitário

**Escopo:** Testa uma **pequena unidade** de código isoladamente.

**Unidade pode ser:**

- Uma função
- Um método
- Uma classe
- Um módulo

**Características:**

- **Escritor**: desenvolvedor
- **Tempo**: durante desenvolvimento (TDD ou após)
- **Ferramenta**: JUnit, NUnit, pytest, etc.
- **Execução**: millissegundos
- **Cobertura**: específica (não testa integração)

**Exemplo Java:**

```java
@Test
public void testCalcularDesconto() {
    // Arrange
    Produto p = new Produto("Livro", 100.0);
    
    // Act
    double desconto = p.calcularDesconto(0.10);
    
    // Assert
    assertEquals(10.0, desconto);
}
```

**Vantagens:**

- Feedback imediato
- Fácil debugar
- Executa rápido
- Pode testar edge cases facilmente

**Limitações:**

- Não testa integração entre unidades
- Requer mocks/stubs (pode ser frágil)
- Não valida comportamento do sistema

---

### 2. Teste de Integração

**Escopo:** Testa a **interação entre componentes** (módulos, serviços, bases de dados).

**Foco:**

- Dados passam corretamente entre componentes
- Interfaces funcionam
- Comportamento em conjunto está correto

**Características:**

- **Escritor**: desenvolvedor + QA
- **Tempo**: pós-unitário, antes de sistema
- **Ferramenta**: TestNG, Cucumber, requests (HTTP), etc.
- **Execução**: segundos
- **Escopo**: múltiplas unidades + dependências reais

**Exemplo:**

```java
@Test
public void testFluxoPedido() {
    // Integra: REST API + Banco de Dados
    
    // Criar pedido via API
    Pedido p = api.criarPedido(cliente, produtos);
    
    // Verificar se foi salvo no banco
    Pedido pedidoSalvo = db.buscarPorId(p.getId());
    assertNotNull(pedidoSalvo);
    assertEquals(p.getTotal(), pedidoSalvo.getTotal());
}
```

**Desafios:**

- Requer ambiente configurado (DB, servidor)
- Mais lento que unitário
- Falhas podem ser difíceis de debugar
- Dependência de dados (test fixtures)

**Best Practice:**

- Use banco de testes separado
- Limpe dados entre testes
- Use containers (Docker) para ambiente

---

### 3. Teste de Sistema

**Escopo:** Testa o **sistema completo** como um todo (caixa preta).

**Foco:**

- Funcionalidades end-to-end
- Comportamento não-funcional (performance, segurança, usabilidade)
- Interação do usuário

**Características:**

- **Escritor**: QA, tester
- **Tempo**: pós-integração, antes de produção
- **Ferramenta**: Selenium, Cypress, Appium, etc.
- **Execução**: minutos a horas
- **Escopo**: sistema inteiro, ambiente produção-like

**Exemplo (Web):**

```gherkin
Cenário: Usuário completa fluxo de compra
  Dado que estou na página inicial
  Quando busco por "livro Python"
  E adiciono primeiro resultado ao carrinho
  E vou para checkout
  E preencho dados de entrega
  E preencho dados de pagamento
  Então recebo confirmação de pedido
  E recebo email de confirmação
```

**Vantagens:**

- Testa experiência real do usuário
- Encontra problemas de integração
- Valida requisitos de negócio

**Limitações:**

- Lento
- Frágil (UI muda fácil)
- Difícil debugar (múltiplas camadas)
- Não testa casos muito específicos

---

### 4. Teste de Aceitação (UAT)

**Escopo:** Valida se o sistema **satisfaz as necessidades do usuário**.

**Foco:**

- Requisitos de negócio
- Casos de uso reais
- Satisfação do usuário

**Características:**

- **Escritor**: cliente, product owner, tester
- **Tempo**: antes de release, com usuários reais
- **Método**: manual, exploratório
- **Ambiente**: produção (ou staging próximo)

**Exemplo:**

```
Requisito: Gestão de pedidos de vendedores

Caso de Aceição 1:
  Vendedor consegue criar novo pedido com múltiplos itens
  e recebe confirmação via email
  
Caso de Aceitação 2:
  Vendedor consegue editar pedido antes de ser enviado
  
Caso de Aceitação 3:
  Vendedor não consegue editar pedido já enviado
  (sistema mostra erro apropriado)
```

**Quem faz:**

- Cliente realiza teste
- Product Owner valida requisitos
- Tester prepara cenários

**Aceite significa:**

- Cliente autoriza release
- Requisitos foram atendidos
- Sistema está pronto para produção

## Pirâmide de Testes

A **Pirâmide de Testes** é um conceito visual que mostra a **proporção ideal** de cada nível.

### Estrutura

```
              ▲ Mais caro, lento, integrado
              │
         ┌────┴────┐
         │   E2E   │  Manual Tests (poucos)
         ├────┬────┤
         │ UI │    │  Testes de Sistema/Integração (médios)
         ├────┴────┤
         │  UNIT   │  Testes Unitários (muitos)
         └────┬────┘
              │
              ▼ Mais barato, rápido, isolado
```

### Proporção Ideal

- **70%** Testes Unitários
- **20%** Testes de Integração
- **10%** Testes E2E (Aceitação/Sistema)

### Por quê essa proporção?

**Testes Unitários (70%):**

- Baratos (execução rápida)
- Fáceis de manter
- Feedback imediato
- Cobrem lógica específica

**Testes de Integração (20%):**

- Validam interações
- Mais caros que unitário
- Importante para fluxos críticos

**Testes E2E (10%):**

- Caros (ambiente, manutenção)
- Lentos
- Usados apenas para fluxos críticos
- Teste de aceitação final

### Anti-Padrão: Pirâmide Invertida

```
        ▲  Muitos E2E
        │
    ┌───┴───┐
    │       │  Poucos Integração
    ├───┬───┤
    │   │   │  Alguns Unitários
    └───┴───┘
        │
        ▼
```

**Problemas:**

- E2E são caros e lentos
- Feedback demora horas
- Manutenção é pesada
- Fragmentado (não testa unidades)

## Aplicação Prática em Spring Boot

Para um projeto backend em **Spring Boot**, a estratégia seria:

### Unitários (70%)

```java
@Test
public void testValidarEmail() {
    assertTrue(validador.isEmailValido("test@test.com"));
    assertFalse(validador.isEmailValido("invalid"));
}
```

### Integração (20%)

```java
@SpringBootTest
public class PedidoServiceIntegrationTest {
    @Test
    public void testCriarPedidoSalvaNoDb() {
        Pedido p = service.criar(cliente, produtos);
        assertEquals(p, repository.findById(p.getId()));
    }
}
```

### E2E (10%)

```java
@Test
public void testFluxoCompraCompleto() {
    // REST API end-to-end
    Response res = client.post("/api/pedidos", pedidoDto);
    assertEquals(201, res.statusCode());
}
```

## Resumo dos Conceitos-Chave

|Conceito|Definição|Aplicação|
|---|---|---|
|**Erro**|Ação humana incorreta|Prevenção via treinamento|
|**Defeito**|Código/artefato com problema|Encontrado por teste|
|**Falha**|Sistema não funciona|Impacto no usuário|
|**V&V**|Verificação (como) + Validação (certo)|Dupla garantia de qualidade|
|**Shift-Left**|Testes cedo no ciclo|Economia de custos|
|**RCA**|Análise de causa-raiz|Melhorias sistêmicas|
|**Pirâmide**|70% unitário, 20% integração, 10% E2E|Equilíbrio custo/benefício|
