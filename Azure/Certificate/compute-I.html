MÓDULO 01 / 01

A arquitetura base do App Service

O Azure App Service é uma plataforma PaaS — Platform as a Service utilizada para hospedar aplicações web, APIs e backends sem que você precise administrar diretamente a infraestrutura física ou o sistema operacional da máquina.

Ideia principal Você se concentra na aplicação. O Azure administra grande parte da infraestrutura necessária para executar essa aplicação.
Infraestrutura de execução

App Service Plan

Define a capacidade computacional utilizada pelas aplicações.

  • SKU / Tier
  • Quantidade de instâncias
  • Região
  • Recursos computacionais
  • Algumas funcionalidades disponíveis
Aplicação

Web App

É o recurso onde sua aplicação é hospedada dentro do App Service.

  • Aplicação web
  • API
  • Configurações
  • Deployment
  • Domínio

Como pensar na arquitetura

Modelo mental 
App Service Plan
│
├── Web App A
├── Web App B
├── Web App C
└── Web App D

Um único App Service Plan pode hospedar múltiplos Web Apps.

Portanto, o Plan representa a infraestrutura/capacidade compartilhada, enquanto o Web App representa uma aplicação executada nessa infraestrutura.

Pegadinha de prova O Web App não é o equivalente direto a uma máquina virtual. Você não está criando uma VM individual para cada aplicação. O modelo do App Service abstrai grande parte dessa infraestrutura.
MÓDULO 01 / 02

O problema do Noisy Neighbor

Como vários Web Apps podem compartilhar o mesmo App Service Plan, eles também podem compartilhar a capacidade computacional fornecida por esse plano.

Cenário compartilhado 
App Service Plan
│
├── API de vendas
├── API de usuários
├── Painel administrativo
└── Site institucional

       ↓

Recursos computacionais compartilhados

Imagine que a API de vendas comece a receber uma quantidade enorme de requisições e passe a consumir muitos recursos.

As outras aplicações estão compartilhando a mesma infraestrutura do plano e podem sofrer impacto dependendo da carga e dos limites do ambiente.

Noisy Neighbor O conceito descreve o risco de uma carga intensa em uma aplicação afetar outras aplicações que compartilham os mesmos recursos de infraestrutura.

Como reduzir o problema?

01

Separar Plans

Aplicações críticas podem ser colocadas em App Service Plans separados.

02

Escalar

A capacidade do Plan pode ser aumentada ou o número de instâncias pode ser ampliado.

03

Arquitetura

Serviços com requisitos diferentes podem ser isolados de acordo com suas necessidades.

Regra mental Vários Web Apps no mesmo Plan = compartilhamento da capacidade do Plan. Plans diferentes = capacidade separada.
MÓDULO 01 / 03

Movimentando um Web App entre Plans

Um Web App pode ser associado a outro App Service Plan, mas existem restrições importantes.

O ponto mais importante

O App Service Plan de origem e o de destino precisam estar na mesma região para uma mudança direta de Plan. A região é uma propriedade fundamental do App Service Plan e influencia onde a infraestrutura da aplicação será executada.

Outras compatibilidades

Aspecto O que verificar?
Região O Plan de destino deve estar na mesma região para a movimentação direta.
SO Verifique a compatibilidade entre o sistema operacional do Web App e o Plan de destino.
SKU O Plan de destino precisa oferecer suporte às características necessárias pela aplicação.
Recursos Alguns recursos específicos podem possuir requisitos ou limitações próprias.
Atenção para prova Não memorize simplesmente "Web App pode ir para qualquer Plan". A associação depende das características e compatibilidade dos recursos envolvidos.
MÓDULO 01 / 04

Scale Up vs Scale Out

Escalabilidade significa aumentar a capacidade da aplicação para atender uma demanda maior.

Scale Up

Também chamado de vertical scaling.

S1
→
P1

Você aumenta a capacidade da infraestrutura associada ao Plan alterando seu SKU/Tier.

Exemplo:

S1 → S2

S2 → P1

Scale Out

Também chamado de horizontal scaling.

#1
#2
#3

Você aumenta o número de instâncias que executam a aplicação.

Exemplo:

1 instância → 3 instâncias

Comparação

Característica Scale Up Scale Out
Tipo Vertical Horizontal
O que muda? Capacidade do Plan Número de instâncias
Exemplo S1 → P1 2 → 5 instâncias
Objetivo Mais capacidade por instância Mais instâncias processando carga
Não confunda Alterar o SKU do App Service Plan é Scale Up. Aumentar o número de instâncias é Scale Out.
MÓDULO 01 / 05

Autoscale e o efeito catraca

O Azure permite automatizar o número de instâncias de uma aplicação de acordo com determinadas métricas ou regras.

Exemplo

Regra de Scale Out 
Se CPU > 70%
durante determinado período

        ↓

Adicionar instância

        ↓

2 → 3 → 4 instâncias

Mas existe um segundo problema:

Scale Out sem Scale In Se você cria regras apenas para adicionar instâncias, o ambiente pode permanecer escalado mesmo depois que a demanda diminuir. Isso pode aumentar o custo desnecessariamente.

Modelo correto

Scale Out + Scale In 
                DEMANDA

                  ↑

        CPU > 70%
              │
              ▼
        SCALE OUT
              │
              ▼
       2 → 3 → 4

              │

        CPU < 30%
              │
              ▼
        SCALE IN
              │
              ▼
       4 → 3 → 2
Regra mental Autoscale deve considerar tanto o crescimento quanto a redução da demanda.
MÓDULO 01 / 06

Deployment Slots

Deployment Slots permitem manter diferentes versões de uma aplicação dentro do mesmo App Service.

Um uso clássico é possuir uma versão de produção e uma versão de staging.

Production

Versão atualmente utilizada pelos usuários.

https://app.azurewebsites.net
⇄

Staging

Ambiente utilizado para testar a nova versão antes de colocá-la em produção.

https://app-staging.azurewebsites.net

O que acontece durante um Swap?

O Swap troca as configurações e o conteúdo operacional associado aos slots de acordo com o comportamento do App Service.

Isso permite promover uma versão que estava em staging para produção sem precisar realizar um deployment convencional diretamente sobre o slot de produção.

Objetivo Reduzir riscos durante deployments e permitir estratégias como staging → production, blue/green e validação prévia da aplicação.

Exemplo de fluxo

Deployment workflow 
                    NOVA VERSÃO
                         │
                         ▼
                    ┌─────────┐
                    │ STAGING │
                    └────┬────┘
                         │
                    Testes / QA
                         │
                         ▼
                       SWAP
                         │
                         ▼
                  ┌────────────┐
                  │ PRODUCTION │
                  └────────────┘
MÓDULO 01 / 07

Slot Settings

Deployment Slots criam um problema importante: determinadas configurações precisam permanecer específicas de cada ambiente.

Exemplo

Imagine que a aplicação possui:

Variável Staging Production
DATABASE_URL Banco de testes Banco de produção
API_KEY Chave de staging Chave de produção

Durante um Swap, você não quer que a configuração do banco de testes seja levada para produção.

Deployment Slot Setting Ao marcar uma configuração como específica do slot, ela permanece vinculada àquele slot durante o Swap.

Modelo mental

Configuração normal vs Slot Setting 
CONFIGURAÇÃO NORMAL
────────────────────

Staging ──Swap──→ Production

A configuração participa
da operação de Swap.


SLOT SETTING
────────────────────

Staging ──Swap──→ Production

A configuração permanece
presa ao seu slot.
Pegadinha de prova Não pense em Slot Setting como "uma configuração que nunca muda". Pense em:

"Essa configuração pertence a este slot."
MÓDULO 01 / 08

Azure CLI

O Azure CLI permite administrar recursos do Azure através do terminal.

Para App Service, dois grupos de comandos aparecem constantemente:

AS

az appservice plan

Trabalha principalmente com App Service Plans.

WA

az webapp

Trabalha principalmente com Web Apps.

Criar um App Service Plan

az appservice plan 
az appservice plan create \
  --name meu-app-plan \
  --resource-group meu-rg \
  --location brazilsouth \
  --sku B1

Aqui você está criando a infraestrutura lógica que fornecerá capacidade ao Web App.

Listar App Service Plans

az appservice plan 
az appservice plan list \
  --resource-group meu-rg \
  --output table

Ver detalhes do Plan

az appservice plan 
az appservice plan show \
  --name meu-app-plan \
  --resource-group meu-rg

Scale Up

az appservice plan 
az appservice plan update \
  --name meu-app-plan \
  --resource-group meu-rg \
  --sku P1v3

Alterar o SKU significa alterar a capacidade/tier do App Service Plan.

Scale Out

az appservice plan 
az appservice plan update \
  --name meu-app-plan \
  --resource-group meu-rg \
  --number-of-workers 3

Agora o conceito é diferente: estamos aumentando o número de instâncias/workers.

Criar Web App

az webapp 
az webapp create \
  --name minha-api \
  --resource-group meu-rg \
  --plan meu-app-plan \
  --runtime "PYTHON:3.12"

O Web App é associado ao App Service Plan informado através de --plan.

Listar Web Apps

az webapp 
az webapp list \
  --resource-group meu-rg \
  --output table

Ver Web App

az webapp 
az webapp show \
  --name minha-api \
  --resource-group meu-rg

Configurar variável de ambiente

az webapp config 
az webapp config appsettings set \
  --name minha-api \
  --resource-group meu-rg \
  --settings ENVIRONMENT=production

Criar Deployment Slot

az webapp deployment slot 
az webapp deployment slot create \
  --name minha-api \
  --resource-group meu-rg \
  --slot staging

Configurar variável em um Slot

az webapp config 
az webapp config appsettings set \
  --name minha-api \
  --resource-group meu-rg \
  --slot staging \
  --settings DATABASE_URL="database-staging"

Realizar Swap

az webapp deployment slot 
az webapp deployment slot swap \
  --name minha-api \
  --resource-group meu-rg \
  --slot staging \
  --target-slot production

Esse comando troca o slot especificado com o slot de destino.

Configurar logs

az webapp log 
az webapp log config \
  --name minha-api \
  --resource-group meu-rg \
  --application-logging filesystem

Deployment via ZIP

az webapp 
az webapp deploy \
  --name minha-api \
  --resource-group meu-rg \
  --src-path ./app.zip

Desafio prático

Agora imagine que você trabalha como DevOps em uma empresa que possui uma API Python.

Requisito A empresa deseja hospedar a API no Azure App Service. O time precisa ter um ambiente de staging e outro de produção.

Sua missão

  • Criar um Resource Group.
  • Criar um App Service Plan.
  • Criar um Web App Python.
  • Criar um slot chamado staging.
  • Configurar uma variável DATABASE_URL.
  • Configurar uma DATABASE_URL diferente para staging.
  • Fazer deploy da aplicação no staging.
  • Testar a aplicação.
  • Executar um Swap.
  • Verificar o comportamento após o Swap.
  • Remover os recursos quando terminar o laboratório.
Objetivo do laboratório Não memorize apenas os comandos. Você deve conseguir explicar por que cada recurso existe e qual problema ele resolve.

Regra de ouro

Para entender App Service, pense em três camadas:

Plan = capacidade
Web App = aplicação
Slot = versão/ambiente da aplicação

Depois conecte isso com:

Scale Up → capacidade
Scale Out → quantidade
Autoscale → automatização
Swap → promoção de versão
Slot Setting → configuração presa ao ambiente
