Azure SQL Database (PaaS)

Guia prático de provisionamento via Azure CLI, replicação geográfica, failover automático, retenção de backups e conexões externas.

O que é o Azure SQL Database?

O Azure SQL Database é um banco de dados relacional totalmente gerenciado (PaaS) baseado na engine do Microsoft SQL Server e otimizado para a nuvem. Ele elimina a necessidade de gerenciar hardware físico, sistemas operacionais, aplicação de patches e manutenções manuais.

Alta Disponibilidade (99,99%)

Garantia de SLA corporativo com replicação interna de nós e failover automatizado sem intervenção humana.

Backup e PITR Automático

Backups completos, diferenciais e de log contínuos, com suporte a recuperação point-in-time e retenção de longo prazo.

Escalabilidade Elástica

Ajuste dinâmico de computação e armazenamento sem downtime para atender picos sazonais de tráfego.

Segurança em Camadas

Firewall por IP, regras de rede virtual, criptografia transparente de dados (TDE) e integração com Microsoft Defender.

Modelos de Implantação do SQL no Azure

Modelo Categoria Caso de Uso Recomendado Nível de Administração
SQL Server on Azure VM IaaS (Virtual Machines) Migrações lift-and-shift diretas que exigem acesso total ao sistema operacional e configurações de baixo nível. Alto (Gerenciado pelo cliente)
Azure SQL Managed Instance PaaS (Quase 100% compatível) Modernização de aplicações existentes com suporte a SQL Agent, CLR, Cross-database queries e Linked Servers. Médio (Sem SO, mas com gestão de instância)
Azure SQL Database (Single / Elastic) PaaS (Banco de Dados Isolado) Novas aplicações em nuvem, microserviços e bancos desacoplados com escalabilidade sob demanda e baixo custo. Mínimo (Totalmente gerenciado)
SQL Database Server vs SQL Database

O SQL Database Server atua como ponto administrativo central (control plane lógico) para hospedar múltiplos bancos isolados. Ele gerencia logins, credenciais de administrador, regras de firewall, auditoria e grupos de failover. O SQL Database é o data plane individual onde residem as tabelas, índices e dados gravados.

Modelos de Compra: DTU vs vCore

Característica Modelo DTU (Database Transaction Unit) Modelo vCore (Virtual Core)
Conceito Métrica combinada e empacotada de CPU, Memória RAM e taxa de E/S de disco (I/O). Alocação transparente de núcleos virtuais de CPU dedicados, memória RAM e storage independente.
Camadas de Serviço Basic (5 DTUs), Standard (10–3000 DTUs), Premium (125–4000 DTUs). General Purpose, Business Critical, Hyperscale (até 100 TB) e Serverless.
Indicação Aplicações com cargas de trabalho simples, orçamentos fixos e requisitos previsíveis. Aplicações corporativas que exigem flexibilidade, alta concorrência e controle granular.

Arquitetura de Replicação e Failover Geográfico

Para garantir tolerância a desastres e continuidade de negócio, o banco de dados primário é replicado assincronamente para uma região secundária emparelhada, configurando um Failover Group com chaveamento transparente de DNS.

1. Servidor SQL Primário (East US 2) Hospeda a réplica primária de leitura e escrita (Read-Write Database) Primário
2. Replicação Geográfica Assíncrona Sincronização contínua de transações com redundância local de storage Geo-Replication
3. Servidor SQL Secundário (West US 2) Hospeda a réplica somente-leitura pronta para assumir a operação Secundário
4. Grupo de Failover (Failover Group) Gerencia o roteamento automático de tráfego em caso de indisponibilidade regional DNS Roteado

Passo a Passo: Provisionamento e Configuração

1. Provedor de Recursos e Grupo de Recursos

bashAzure CLI — Setup Inicial
# Registrar o provedor SQL na assinatura (executar uma única vez)
az provider register --namespace Microsoft.Sql

# Criar o Grupo de Recursos na região East US 2
az group create --name rg-sql-dimdim --location eastus2

2. Servidor Lógico SQL Primário

bashAzure CLI — Servidor Primário
az sql server create \
  --name sql-server-dimdim-rm9999-eastus2 \
  --resource-group rg-sql-dimdim \
  --location eastus2 \
  --admin-user user-dimdim \
  --admin-password 'Fiap@2tdsvms' \
  --enable-public-network true
Requisitos de Complexidade da Senha

A senha do administrador deve ter entre 8 e 128 caracteres, conter caracteres de pelo menos 3 categorias (maiúsculas, minúsculas, números e símbolos) e não pode conter partes do nome do usuário.

3. Criação do Banco de Dados SQL

bashAzure CLI — Database Creation
az sql db create \
  --resource-group rg-sql-dimdim \
  --server sql-server-dimdim-rm9999-eastus2 \
  --name db-dimdim \
  --service-objective Basic \
  --backup-storage-redundancy Local \
  --zone-redundant false

4. Regra de Firewall do Servidor

bashAzure CLI — Firewall Rule
# Liberar acesso para conexões externas (Ambiente de Desenvolvimento)
az sql server firewall-rule create \
  --resource-group rg-sql-dimdim \
  --server sql-server-dimdim-rm9999-eastus2 \
  --name liberaGeral \
  --start-ip-address 0.0.0.0 \
  --end-ip-address 255.255.255.255

Políticas de Retenção de Backup a Longo Prazo (LTR)

Por padrão, o Azure SQL mantém backups automáticos diários com retenção de 7 dias (PITR). A política LTR (Long-Term Retention) estende a retenção para atender a requisitos regulatórios e de compliance.

bashAzure CLI — Definir Política LTR
# Configurar retenção: 30 dias (semanal), 365 dias (mensal) e 5 anos (anual)
az sql db ltr-policy set \
  --resource-group rg-sql-dimdim \
  --server sql-server-dimdim-rm9999-eastus2 \
  --name db-dimdim \
  --weekly-retention P30D \
  --monthly-retention P365D \
  --yearly-retention P1825D \
  --week-of-year 1

# Exibir a política LTR configurada em formato de tabela
az sql db ltr-policy show \
  --resource-group rg-sql-dimdim \
  --server sql-server-dimdim-rm9999-eastus2 \
  --name db-dimdim -o table
ParâmetroDuração / Significado
--weekly-retention P30DMantém os backups semanais armazenados por 30 dias (1 mês).
--monthly-retention P365DMantém os backups mensais armazenados por 365 dias (1 ano).
--yearly-retention P1825DMantém os backups anuais armazenados por 1825 dias (5 anos).
--week-of-year 1Indica que o backup anual de referência será extraído na 1ª semana do ano.

Configuração do Grupo de Failover (Failover Group)

1. Criar o Grupo de Failover

bashAzure CLI — Criar Failover Group
az sql failover-group create \
  --name failover-group-dimdim-rm9999 \
  --resource-group rg-sql-dimdim \
  --server sql-server-dimdim-rm9999-eastus2 \
  --partner-server sql-server-dimdim-rm9999-westus2 \
  --partner-resource-group rg-sql-dimdim \
  --failover-policy Automatic \
  --grace-period 1
Grace Period

O --grace-period define o tempo em horas (mínimo de 1 hora) que a Azure aguarda após detectar uma falha no servidor primário antes de acionar o failover automático com possível perda de dados assíncronos pendentes.

2. Associar o Banco de Dados ao Grupo

bashAzure CLI — Associar DB ao Failover Group
az sql failover-group update \
  --name failover-group-dimdim-rm9999 \
  --resource-group rg-sql-dimdim \
  --server sql-server-dimdim-rm9999-eastus2 \
  --add-db db-dimdim
