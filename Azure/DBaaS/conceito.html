Azure SQL Database (DBaaS)

Conceitos fundamentais de banco de dados como serviço, arquitetura desacoplada e integração limpa com o backend.

1. O Paradigma DBaaS (Separação de Responsabilidades)

O conceito central do Database as a Service (PaaS) é a transferência do plano de controle (control plane) para o provedor de nuvem. Em um ambiente on-premise ou IaaS, o banco de dados é um processo rodando sobre um sistema operacional com estado (stateful), exigindo gestão manual de I/O de disco, failover e patching. No DBaaS, a arquitetura é desacoplada.

A nuvem trata a engine do banco de dados como um recurso elástico. O armazenamento físico dos dados (arquivos .mdf, .ndf, .ldf) ocorre em instâncias remotas de storage de alta disponibilidade, enquanto a computação (processamento de queries) roda em clusters efêmeros. Isso garante que, se o nó de processamento falhar, o plano de controle imediatamente anexa o volume de storage a um novo nó saudável, mantendo a consistência do cluster sem intervenção manual.

2. Arquitetura Lógica do Azure SQL

Ao provisionar um banco no Azure, você não cria uma máquina virtual, mas sim instaura uma topologia baseada em anéis de roteamento. O primeiro componente criado é o Logical Server. Ele atua estritamente como um gateway proxy e não consome recursos computacionais por si só.

Quando a sua API realiza uma chamada para o endpoint, a requisição atinge primeiro o gateway. O gateway avalia as regras de firewall e as credenciais. Se autenticado, ele traduz o FQDN para o endereço IP interno do anel de locatário (tenant ring) onde o seu database físico está operando no momento.

bashExemplo Conceitual: Gateway vs Database
# 1. O Servidor Lógico é apenas um roteador (Control Plane / Gateway)
az sql server create \
  --name gateway-logico-db \
  --resource-group rg-backend-db \
  --location eastus \
  --admin-user "dbadmin" \
  --admin-password "S3nh@F0rt3!"

# 2. O Database é onde a computação e o armazenamento real residem (Data Plane)
az sql db create \
  --resource-group rg-backend-db \
  --server gateway-logico-db \
  --name database-real \
  --edition GeneralPurpose \
  --compute-model Serverless \
  --capacity 2 \
  --min-capacity 0.5 \
  --auto-pause-delay 60
Proxy Connection Policy

Por padrão, conexões externas usam a política "Proxy". O tráfego passa pelo gateway do Azure antes de chegar ao nó de banco de dados (porta 1433). Em VNets internas, pode-se usar a política "Redirect", onde o cliente obtém o IP direto do nó, reduzindo a latência pulando o gateway em requisições subsequentes.

3. Motor Computacional: A Lógica do Serverless

Na modelagem de recursos vCore Serverless, o provedor desacopla totalmente CPU/Memória do armazenamento subjacente. A lógica opera com base em um limite mínimo e máximo de vCores. O monitoramento interno do Azure observa o tráfego da porta 1433; se a demanda de queries subir, o cluster aloca dinamicamente mais processadores do pool compartilhado para a sua instância.

A mecânica de Auto-pause ilustra perfeitamente essa abstração. Se nenhuma sessão ativa for registrada durante o período de auto-pause-delay, o Azure destrói a instância computacional temporariamente, persistindo apenas o armazenamento no Azure Premium Blob Storage. Na próxima requisição da API (o chamado cold start), a nuvem provisiona uma nova instância computacional e reconecta o storage em segundos.

bashComportamento Parametrizado
# Parâmetros lógicos que definem a elasticidade do motor
az sql db create \
  --resource-group rg-backend-db \
  --server gateway-logico-db \
  --name database-real \
  --edition GeneralPurpose \
  --compute-model Serverless \
  --capacity 4 \           # Limite máximo de alocação de CPU (vCores)
  --min-capacity 0.5 \     # Piso mínimo de operação
  --auto-pause-delay 60    # Pausa a computação após 60 min de inatividade

4. O Papel da Camada de Infraestrutura no Backend

Seguindo a Clean Architecture, o banco de dados é um detalhe externo. A aplicação ignora se o banco está rodando em um container local, H2 em memória, ou gerenciado pelo Azure. A injeção de dependência via repositórios abstrai a implementação do framework (Hibernate ou SQLAlchemy). A única fronteira lógica entre sua aplicação e o DBaaS é o protocolo de rede manipulado pelo ORM através da connection string, que garante a criptografia ponta-a-ponta.

pythonFronteira Lógica (Clean Architecture)
# domain/entities/user.py
# Entidades de domínio desconhecem a infraestrutura DBaaS
class User:
    def __init__(self, id: int, name: str):
        self.id = id
        self.name = name

# infrastructure/database/connection.py
# Apenas a camada de infraestrutura conhece as regras de comunicação com o Azure
import urllib.parse
from sqlalchemy import create_engine

def get_db_engine():
    params = urllib.parse.quote_plus(
        "Driver={ODBC Driver 18 for SQL Server};"
        "Server=tcp:gateway-logico-db.database.windows.net,1433;"
        "Database=database-real;"
        "Uid=dbadmin;"
        "Pwd=S3nh@F0rt3!;"
        "Encrypt=yes;"
        "TrustServerCertificate=no;"
        "Connection Timeout=30;"
    )
    return create_engine(f"mssql+pyodbc:///?odbc_connect={params}")

5. Resumo de Conceitos Teóricos

Conceito Mecânica Lógica no DBaaS
Control PlaneInfraestrutura interna do provedor que gerencia rotinas, failovers e métricas sem interação direta do usuário.
Data PlaneA instância alocada onde suas queries efetivamente rodam e seus dados residem.
Cold StartAtraso inicial na resposta da primeira query após a camada Serverless sair do estado de auto-pause.
Connection StringContrato técnico que instrui o driver da aplicação (ex: JDBC ou ODBC) sobre como negociar a conexão TCP na porta 1433 com o gateway lógico.
