Azure Containers DevOps Cloud Architecture Serverless
Resumo Executivo

A combinação do Azure Container Registry (ACR) com o Azure Container Instances (ACI) viabiliza a execução de aplicações containerizadas sob o modelo serverless. O ACR atua como o repositório privado para governança de docker images, enquanto o ACI fornece o motor de execução isolado sem a necessidade de gerenciar servidores, VMs ou a complexidade de um cluster de Kubernetes (AKS).

Funcionamento Interno (Under the Hood)

Azure Container Registry (ACR)
  • Armazenamento e Criptografia: Armazena docker images e artefatos compatíveis com OCI. As imagens são salvas com criptografia automática (at rest).
  • Controle de Acesso: Autenticação nativa com Microsoft Entra ID (Azure AD) via Service Principals, Managed Identities ou credenciais administrativas.
  • CI/CD Nativo (ACR Tasks): Atua como um pipeline automático. Ao configurar uma task vinculada ao GitHub, commits acionam o webhook do ACR, compilando o Dockerfile e gerando a nova tag diretamente na nuvem.
Azure Container Instances (ACI)
  • Isolamento de Hypervisor: Cada grupo de containers roda em uma mini-VM dedicada (utility VM), garantindo isolamento total em nível de kernel.
  • Alocação e Faturamento: Especificação exata de vCPUs e memória RAM com faturamento por segundo de execução (per-second billing).
  • Rede e Exposição: Mapeamento direto de IP público e suporte a FQDN para exposição de endpoints HTTP/HTTPS.
Persistência de Estado e Injeção de Segredos
  • Persistência de Dados (Volumes): Como containers ACI são temporários (ephemeral), bancos relacionais como o MySQL utilizam montagem de file share via protocolo SMB provisionado no Azure Files, mapeando a pasta /var/lib/mysql.
  • Segurança de Credentials: Segredos e connection strings são armazenados no Azure Key Vault e injetados na inicialização do container como environment variables.

Trade-Offs Arquiteturais

Aspecto Vantagens Limitações
OpEx & Infraestrutura Sem gestão de nós, atualizações de SO ou manutenção de clusters. Menos controle fino sobre parâmetros de rede e kernel do SO.
Tempo de Subida Cold start rápido (poucos segundos). O download inicial da imagem (pull) pode gerar atrasos se o tamanho do artefato for elevado.
Escalabilidade Ideal para cargas pontuais (batch jobs) e microsserviços simples. Ausência de auto-scaling horizontal avançado e rolling updates nativos sem queda de serviço.
I/O de Banco de Dados Facilidade para criar ambientes de dev/test com persistência em Azure Files. Latência do protocolo SMB em volumes montados pode limitar a taxa de transações (IOPS) em produção.

2. Comandos Essenciais e Guia de Referência

Pipeline de Imagens (Build, Tag e Push)

bash - Pipeline Docker & ACR 
# Autenticar a CLI na conta da Azure
az login

# Realizar o login no registro privado do ACR
az acr login --name moneyhubrm9999

# Criar tags direcionando as imagens locais para o namespace do ACR
docker tag mysql-dimdim moneyhubrm9999.azurecr.io/mysql-dimdim:v1
docker tag api-dimdim moneyhubrm9999.azurecr.io/api-dimdim:v1
docker tag api-transacoes moneyhubrm9999.azurecr.io/api-transacoes:v1

# Enviar as imagens marcadas para o repositório remoto no ACR
docker push moneyhubrm9999.azurecr.io/mysql-dimdim:v1
docker push moneyhubrm9999.azurecr.io/api-dimdim:v1
docker push moneyhubrm9999.azurecr.io/api-transacoes:v1

# Listar todos os repositórios cadastrados no ACR
az acr repository list --name moneyhubrm9999 --output table

# Exibir todas as tags disponíveis de um repositório específico
az acr repository show-tags --name moneyhubrm9999 --repository mysql-dimdim

Gestão e Diagnóstico de Containers no ACI

bash - Inspecionar & Executar ACI 
# Acompanhar os logs da aplicação em tempo real (streaming)
az container logs --resource-group rg-money-hub --name api-java --follow

# Iniciar uma sessão interativa bash dentro do container no ACI
az container exec --resource-group rg-money-hub --name api-java --exec-command "/bin/bash"

# Executar verificação de processos ativos dentro do container
az container exec --resource-group rg-money-hub --name api-java --exec-command "ps aux"

# Testar requisição HTTP interna diretamente do container
az container exec --resource-group rg-money-hub --name api-java --exec-command "curl -X GET http://localhost:8080/api/transacoes"

# Extrair o FQDN e IP Público atribuídos à instância do container
fqdndotnet=$(az container show --resource-group rg-money-hub --name api-dotnet --query ipAddress.fqdn --output tsv)
echo "FQDN da API: $fqdndotnet"

3. Desafios e Exercícios de Fixação

Cenário 1: Gargalo de I/O na Gravação do Banco de Dados

Situação: O container do MySQL rodando no ACI apresenta alta latência em operações de escrita intensiva. A investigação mostrou que a pasta /var/lib/mysql está montada em um file share do Azure Files via SMB.

Exercício: Identifique a causa técnica da limitação de I/O e descreva a arquitetura recomendada para rodar o database em ambiente produtivo mantendo as APIs no ACI.

Cenário 2: Exposição de Credenciais no Script de Deploy

Situação: Um pipeline de CI/CD injeta a senha administrativa do banco via texto claro no parâmetro --environment-variables MYSQL_PASSWORD=senha123 na CLI.

Exercício: Explique o risco de vazamento dessa informação nos registros do Azure Resource Manager (ARM) e reestruture o fluxo para realizar a injeção segura via Azure Key Vault e Managed Identity.

Cenário 3: Indisponibilidade no Deploy de Novas Versões

Situação: Ao efetuar o push da versão v2 de uma API e recriar o container no ACI, a aplicação passa por um período de downtime até a nova instância concluir o startup.

Exercício: Como contornar a ausência de rolling update nativo no ACI para alcançar uma estratégia de zero-downtime deployment utilizando roteamento de tráfego?

Cenário 4: Otimização de Imagem Docker (Redução do Cold Start)

Situação: A docker image de uma API .NET ocupa 850 MB no ACR, fazendo com que o tempo de pull no ACI atrase a inicialização do serviço (cold start).

Exercício: Escreva o conceito de um Dockerfile otimizado aplicando a técnica de Multi-Stage Build e utilização de imagens base lightweight.

4. Gabarito e Solução dos Cenários

Respostas dos cenários abaixo
Solução do Cenário 1: Gargalo de I/O na Gravação

Análise Técnica: O protocolo SMB via rede introduz alta latência de travamento de arquivo e sincronização por pacotes TCP, limitando severamente os IOPS em comparação com discos em bloco local.

Arquitetura Recomendada: Para ambientes produtivos, substitua o MySQL em ACI por um serviço PaaS gerenciado como o Azure Database for MySQL (Flexible Server), que utiliza armazenamento de alta performance (*Premium SSD*) e *auto-healing*, mantendo as APIs no ACI conectadas via String de Conexão segura.

Solução do Cenário 2: Exposição de Credenciais no Deploy

Análise Técnica: Variáveis passadas via parâmetro da CLI ficam registradas nos históricos do runner de CI/CD e na API auditável do ARM em texto claro.

Refatoração Segura: Armazene a senha no Azure Key Vault. Em seguida, habilite uma Managed Identity na instância do ACI e conceda a permissão de leitura (*Secret User*) no Key Vault. A aplicação lê o segredo via SDK/Identity sem expor segredos nos scripts de deploy.

Solução do Cenário 3: Indisponibilidade no Deploy

Estratégia Blue/Green em ACI:
1. Mantenha a versão v1 rodando no Container Group A (Blue) atendendo o tráfego através de um roteador como Azure Application Gateway ou Azure Traffic Manager.
2. Suba o novo Container Group B (Green) com a versão v2 em paralelo.
3. Execute o teste de disponibilidade (*health check*) na v2.
4. Redirecione o tráfego do roteador para o Container Group B e destrua o Container Group A.

Solução do Cenário 4: Otimização de Imagem Docker

Conceito do Dockerfile Otimizado:
- Use a imagem do SDK completa (ex: mcr.microsoft.com/dotnet/sdk:8.0) apenas na primeira etapa (build stage) para compilar os binários.
- Na etapa final (runtime stage), copie apenas os binários para uma imagem enxuta (ex: mcr.microsoft.com/dotnet/aspnet:8.0-alpine ou distroless).
- Isso reduz o tamanho final de 850 MB para cerca de 100-150 MB, acelerando o *pull* no ACI.
